# 安排：让交代过的工作在约定时间接着发生

## 产品与交付位置

用户交给麻薯的是未来的一次工作或例行跟进：每周五核对发布事项、明天下午检查上线条件、每天整理需要人决定的阻塞。一个安排只有三项核心事实：**做什么、什么时候、结果出现在哪里**。所属 Bot 和群由真实创建位置确定。飞书自然语言负责交代和修改，设置负责查看、暂停、恢复与取消；两处操作同一份记录。

用户的期待同时包含“到时有人接续”和“我能找到结果”。把结果一律藏在原话题，保存了上下文，却把记得回去查看的责任交还给人；新群消息更容易出现在当前阅读位置，但陌生的结论可能打断正在进行的讨论。首版因此采用一个明确的默认：**同一群里的一条新结果，内容自包含，附原讨论链接（真实证据有链接时）**。不先发“开始了”、再发报告，也不同时在群里和旧话题发两份。没有默认 @、催读或“已看见”的声称。

| 人的表达与处境 | 保存的交付方式 | 原因 |
| --- | --- | --- |
| 交代周期进展、约定未来检查，没有指定位置 | 同群新消息 | 让委托有可见的回应，不要求人主动翻旧话题 |
| “以后留在这个话题里”“这里安静跟进” | 发话时所在话题内回复 | “这里”对应人正在操作的对象 |
| “回最初交代的讨论” | 原讨论内回复 | 保留人明确选择的历史位置 |
| 只改时间或工作内容 | 保留已有去向 | 不因修改发生在另一条关联结果下而悄悄移动交付 |

这是一项有理由的设计判断，尚不是用户研究结论。群消息到达不保证通知、已读或注意力，话题回复也不能被宣传为一定唤回所有参与者。最值得在真实使用中验证的是：人能否看见并辨认这是哪份交代，是否反复寻找旧话题，周期结果是否干扰当前协作。若长期结果噪声成为真实问题，再设计可靠的“仅有变化才汇报”；首版不靠猜变化、猜紧急程度或双重通知解决。

结果标题解释“哪件工作”，关键结论和依据组成同一消息，尾部连接原讨论。新结果的讨论被关联到同一个安排，因此下面的“改到周四”“暂停”可以管理已有安排。它不与原话题合并，也不继承原发言者的 GitHub 写入授权。原讨论、各次结果及人类消息保留各自身份与顺序；Bridge 不制造一条人类事件。

## 交代和管理

支持一次性、每天、指定星期；工作日是周一至周五，不猜节假日。周期保存明确的 IANA 时区和当地钟表时间；一次性保存带时区的绝对时间。模型先读安排目录取得当前时间、本机时区和关联安排。Mac 时区只是线索，团队时间或事项有歧义时仅询问缺少的事实。task 必须自包含，写清事项、调查目标和交付物，不保存“这个”“照旧”作为未来工作。

创建成功必须根据真实 readback 回读工作、频率、时区、下一次与交付方式，例如：“已安排：每周五 15:00（上海时间）核对 Issue 20 的发布阻塞，把结论发到这个群。下次 10 月 9 日。”这里只是表达示例，不是时间、项目或授权的默认值。修改时间/内容时 `schedule.update` 省略 `delivery`；明确改位置时再提供。`thread` 绑定当前真实发话位置，`original_thread` 绑定最初讨论，模型不能传任意群、消息或 Bot。

设置中的 **安排** 是 Bot 分类，每项工作用一张低对比度卡片呈现，卡片之间以留白区分。标题和开关状态同排，规则与时区在其下；下次时间、去向和最近交付使用统一对齐的信息列，下次时间优先于历史记录。工作内容入口和取消操作同排，展开后正文占满卡片内容宽度，以接近性和共同区域解释关系。没有另一套创建表单、cron 编辑器、运行历史仪表盘或多步教程。暂停开关只有权威保存和回读后才改变；取消采用一处就地确认。版本冲突保留实际状态并让人看最新内容，断连移除旧列表；切换 Bot 隔离查询和迟到响应。

正常状态显示下一次和最近一次；失败显示固定原因与下一步。**已发出**只表示经过验证的交付回执，不表示已读或事项完成。模型结束、调查成功和消息交付是不同事实。设置能管理该 Bot 的全部安排；群聊只能管理当前原讨论、约定交付话题或关联结果里的安排，不能利用另一个群的授权。

## 执行与故障承诺

- Mac、LaunchAgent 和该 Bot 需要运行。关闭设置窗口不停止后台；关机、睡眠或离线时不承诺准点，不增加唤醒策略、云端服务、cron 或另一个 LaunchAgent。
- 空闲时才领取到点工作；已接受的人类消息先处理。安排与人类 turn 不互相 steer 或合并，全部仍使用该 Bot 的原永久 Pi Session。
- 恢复后，未领取的一次性工作迟到执行一次；周期工作只处理最近一期，并在结果里说明迟到/略过。忙碌越过多个时点也按同一规则合并，不补一串过时报告。
- 固定 Bun 1.4.2 的原生 Temporal 拥有日历计算。夏令时缺失时刻跳过当天，重复时刻只取第一次；系统时区变化不移动保存的约定。15 秒观察间隔处理时钟和睡眠变化，它不是准点保证或周期定义。
- 同一事务领取 `(schedule_id, due_at)` 并推进下一次；执行和交付不确定时记失败/中断，不自动重放或重发。正常的后续周期仍可运行。恢复不删除幂等记录。
- 暂停/取消阻止以后领取，已接受工作仍按当时的定义交付。恢复周期从下一个未来时点开始；过期的一次性安排必须改时间。重复设置当前开关状态不推进时间或丢掉到点工作。
- 每 Bot 最多 50 项，标题 120 字符、工作 4,000 字符、明确资源 20 个，保留最近 20 次执行元数据及相应结果关联。损坏定义、非法时间和基础存储故障失败关闭；设置不能将错误伪装为“没有安排”。

## 权限与所有权

到点工作只调查、总结或提醒。创建/修改经当前人类原话授权、同群话题限制、revision、Broker 幂等和回读；到点本身不重新授予写入权限，不修改 Issue，不创建更多安排。人看到结果后明确要求写回，才按现有当前消息合同执行。

资源在交代时绑定精确 `connectionId/resourceId/selectionId`；新选项目不会扩大已有安排。派发、每次连接器读取和交付前复核当前授权。飞书 App 改变、原群关闭/退出、资源取消选择、重新选择或账号/installation 改变均不能让旧工作借新授权继续。话题交付还须复验目标消息仍属于同群且可访问；不可访问时阻止本次交付并提供重定去向的说明。

worker protocol **10** 的 `turn.start.executionPolicy` 由受信任宿主传入，普通消息为 `interactive`，安排为 `scheduled`。安排的目录只显示绑定资源和只读能力，Bridge 与 worker 分别拒绝 `connector_write`。worker 独立拒绝该 turn 的 `bash/edit/write`，保留原生 `read`、材料只读和闭合的 `web_search/web_fetch`。单禁 bash 不够：scratch 写入可以替换 PATH 中的研究命令，所以写入工具同样关闭。不能以任务文字、网页或永久记忆恢复这些权限。worker 仍在原隔离 OS 用户和沙箱合同内运行。

Bridge 拥有定义、日历、领取和交付状态；Pi 拥有模型循环、永久 Session、JSONL 与自动压缩。SQLite schema **9** 含 `schedules/schedule_runs/schedule_deliveries`。数据库只存明确委托与执行元数据，不复制飞书对话或模型回答。

安排的内置 manifest 经原有四个 Bridge tools 发布 `schedule.list/create/update/pause/resume/cancel`，不改变四工具 schema 或 capability ABI。它是宿主内部能力，不是新的外部账号；companion 的外部连接器目录不展示它。来源位置与交付目标由 Bridge 拥有，模型只解释自然表达。

control protocol **24** 增加带 `botId` 的 `read_schedules/set_schedule_enabled/cancel_schedule`；修改只收安排 ID、revision 和必要的开关值。任务/群名/最近固定状态仅按需通过 mode-600 私有 socket 与受范围校验的 RPC 返回，不进 status、诊断、日志或浏览器持久化。单次 control 上限 1 MiB，覆盖 50 份 4,000 字符 UTF-8 工作；列表不包含人类来源身份、消息 ID、凭据、路径或资源选择身份。host 修改后必须读回。status **28** 不增加安排正文或执行历史；日志仅记录 Bot/安排稳定身份、发生时点和固定原因。

## Pi 生态的取舍

当前固定 `@earendil-works/pi-coding-agent` **1.1.0**。随包 `docs/sdk.md` 与 `dist/core/agent-session.d.ts` 的 `prompt/steer/followUp` 负责 Session 工作与内存队列；未来日历和客户授权属于 Mochi 的宿主合同。

2026-10-03 核查的 [Pi Durable](https://earendil.com/posts/pi-durable/) 已提供持久 timer 与后台工作，其 [README](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md) 标记实验性。它会改变 transcript、恢复、compaction 和重送模型请求的所有权，不能只为安排引入第二权威。首版保留现有 SDK 和 at-most-once；若未来需要跨进程续跑在途工作，应单独评估整个 harness 迁移，而不能声称 Pi 没有持久定时能力。

## 验收边界

确定性验收覆盖日历/DST、事务领取、重启不重放、忙碌与暂停、资源身份、当前授权、结果关联、目标更新与不变、同一 Session、worker 工具门禁、真实私有 socket、大 UTF-8 列表、非 schema 9 数据库失败关闭且不改写，以及 renderer 的 Bot 隔离。BotApp 组合测试通过真实观察时钟、SQLite 和私有 worker/CLI 子进程传输，验证已接受工作在暂停后仍交付，以及执行中群成员权限失效会阻止发送；子进程返回注入的确定性模型与平台响应。WebKit 使用实际 Settings 组件及注入服务事实，检查管理动作、断连、固定失败、过期一次性、迟到响应及 360/1040 宽度的实际截图。

准确提交的完整本地验收由仓库 `bun run verify` 收据记录。以上不是原生 AppKit 材质、真实模型的自然语义判断、飞书到点消息、通知可见性或 Mac 睡眠恢复的现场证据；本次没有安装、替换永久 Session 或在真实群投递测试。部署后的验收需使用用户明确指定的测试群和内容，保留原 Session，观察真实模型选择、回执与同事阅读路径，不以 fixture 代替。

未来扩展必须来自真实需要：仅有变化才回帖需可靠比较语义；任意周期需可解释的日历规则；自动写入需独立、可撤销和可审计的未来授权合同。首版不预建这些框架。
