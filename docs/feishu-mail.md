# 飞书共享邮箱连接器

日期：2026-10-10。

飞书共享邮箱是 Mochi 的独立 `feishu-mail` 连接器。它服务于团队共同处理一个收件箱的场景，例如 `support@example.com`，与飞书群通道、飞书文档/Wiki 服务分别拥有自己的连接器身份、资源选择和能力清单。

## 当前交付

- 授权主体是明确的飞书用户身份（`--as user`），不是飞书机器人身份。机器人只负责 Mochi 已有的飞书传输上下文。
- 资源是用户在飞书实际可访问的公共邮箱（`email_type` 为 `PUBLIC_MAILBOX`）。Mochi 用官方 `accessible_mailboxes` 目录列出它们，用户点选即可；保存前再次核对目录，任意猜测的地址不会进入连接器范围。用户本人的主地址、别名和邮件组不是选项，也不会作为 Bot 事实写入状态。
- 当前只声明两项能力：列出会话（`thread.list`）和读取会话（`thread.read`）。结果有数量、附件和正文长度上限。
- 邮件主题、发件人、正文和附件元数据都标记为外部不可信资料。它们不会成为 Mochi 的指令、授权或身份依据。
- 连接器没有发送、回复、转发、草稿写入、删除、移动、标签、已读状态或收信规则修改能力。`write` 入口也会明确失败关闭；manifest 不发布任何写能力。

这条连接器不改变永久 Pi Session、飞书群参与开关、GitHub 项目选择或已有飞书服务资源。取消邮箱选择只删除 Mochi 保存的范围，不改动飞书邮箱里的邮件。

用户授权与飞书应用本身的权限开通是两件事。用户只能授予应用已开通的用户权限，所以 Mochi 在发起授权前先用官方 `auth scopes --json` 读取应用已开通的用户 scopes：缺少任何一项邮箱读取 scope 时不发起授权，而是给出“需要先在飞书开通邮件读取权限”和“去飞书开通权限”。后者经 `feishu_mail_settings` 打开官方 scope-apply 页（与 lark-cli 1.0.93 为缺失权限构造的页面相同），只带上仍缺少的邮箱 scope。开通后回到 Mochi 再点一次“授权读取邮箱”。如果授权结果仍缺少读取 scope，会话读取能力显示为“尚未获得所需授权”并在 Broker 处失败关闭，页面提供“重新授权”；Mochi 不会把缺失权限降级成写入或绕过权限。

## 实机验收（2026-10-10，早于自动完成授权与列表选择）

- 使用正在运行的 Bot 自己的私有连接证明用户身份有效，官方可访问目录确认包含目标共享邮箱。宿主终端的同名 CLI profile 不代表这个连接。
- 经 Mochi 控制通道重新发起只读授权；飞书官方页面列出新增的邮件、地址、主题和正文读取权限，并确认授权完成。Mochi 完成设备流程后重新证明用户身份。
- 经原有资源选择控制通道保存目标共享邮箱；当前状态确认已选择一个邮箱，`thread.list` 与 `thread.read` 均为 `ready`。
- 使用产品 reader 和同一私有连接，`threads.list` 在 `folder_id=INBOX`、上限 1 下返回一个真实会话；随后 `+thread --html=false` 成功解析该会话的一封邮件及 129 字符纯文本正文。验收输出只记录数量与长度，不保留邮件正文。
- 本次没有调用邮件写入接口。现有 Bot、策略文件和永久 Session binding 在 Bridge 更新前后的摘要相同；飞书事件流恢复为 `ready`。
- 以上证明授权、明确邮箱范围及真实会话读取，不包含在正式群代替用户发言的模型回帖验收。

## 使用路径

在设置的“连接器 → 飞书共享邮箱”中（当前 Bot 的飞书机器人需已连接；从未连接时页面只提供“连接飞书”，连接需要处理时提供“查看飞书连接”，恢复后已有的邮箱授权与选择继续生效）：

1. 点击“授权读取邮箱”。浏览器打开飞书官方授权页，页面同时显示二维码，可用手机飞书扫码。
2. 在飞书中确认只读权限。不需要回到 Mochi 报告：页面显示“确认后这里会自动更新”，Bridge 收到结果后复核用户身份和可访问邮箱目录，页面自动变为已连接。
3. 在“访问范围”列表中打开要读取的邮箱的开关。无需输入地址，也没有刷新按钮：列表按地址固定排序，切换时行不移动；Bot 每分钟及你回到 Mochi 时自动复核授权与可访问目录，被加入新的共享邮箱后它会自动出现。
4. 后续 Agent 只能读取已选择邮箱的会话和正文。取消选择只删除 Mochi 的范围，不改动飞书邮箱。

页面状态与连接器发布的事实一一对应：

| 连接器发布 | 页面 |
| --- | --- |
| `unavailable` + `resource_reconciliation_required`（本次启动或换了飞书应用后还没核对过） | 状态“正在确认”，正在确认邮箱授权 |
| 无邮箱连接（飞书确认没有用户授权，也没有保存的邮箱） | 未连接；“授权读取邮箱” |
| `authorizing` | 二维码、“确认后这里会自动更新”、“在浏览器中打开”、“取消授权”；窗口重开后没有二维码时为“继续授权”，交还同一个进行中的授权 |
| `reauthorization_required` + `mail_authorization_incomplete` | 状态“授权未完成”；“上次授权没有完成，可能已过期或被取消。”；“重新授权” |
| `reauthorization_required` + `authorization_required` | 授权已失效；“重新授权”，已选择的邮箱在复核后恢复读取 |
| `unavailable`（其他） | 暂时无法确认，Mochi 每分钟自动重试，没有手动按钮。已证明身份但目录读取失败且没有已选邮箱时也是这一状态，不显示为空列表 |
| `ready` | 公共邮箱列表，每行一个开关（读取邮件 · 只读 / 不读取），切换中的行显示“正在更新…”；没有可选邮箱时说明需要被加为邮箱成员，加入后自动出现 |
| `ready` + 能力 `authorization_required` | 授权缺少读取 scope；“重新授权” |

已连接时，“连接管理”提供“换一个飞书账号授权”：授权错了账号时走同一个授权流程；等待确认期间连接为 `authorizing`，原授权暂停读取，“取消授权”即恢复。邮箱范围只属于当前证明的账号：新账号复核通过时，其他账号（包括换了飞书应用后的同一个人）保存的邮箱选择会被清除，需要重新选择。

“连接管理”还提供“断开授权…”（原生确认后执行，需 Bot 空闲）：Bridge 用官方 `auth logout` 清除这个连接 profile 下的用户令牌（lark-cli 会尽力请求飞书撤销，撤销失败不阻止本机清除；应用与机器人凭据不受影响），清除全部邮箱选择，再重新复核；复核仍证明有用户身份时如实报错，不假定已断开。成功后页面回到“未连接”。

复核是原子的：重新核对期间继续发布上一次的结论，结果确定后一次替换，所以复核不会让已连接的页面闪成未连接。只有还没核对过（本次启动后或飞书应用绑定变化后）才发布“正在确认”。

授权 URL 和 device code 是短暂的内存状态；device code 不写入 SQLite、status、渲染器或日志。断开/失效时，已保存的邮箱范围保留为不可调用状态，重新确认授权后才恢复读取。

官方 CLI 的 `auth login --no-wait --json` 直接返回 device-flow 字段，不使用 OpenAPI 命令的 `ok/data` 信封。授权模块以有效 device code 和官方 HTTPS 授权 URL 判断发起成功，随即以 `auth login --device-code` 在后台阻塞轮询（lark-cli 1.0.93 每 5 秒一次、本地上限 600 秒；Mochi 的进程期限为 630 秒，取消授权时立即结束该进程）。轮询的退出码不是授权结果：用户拒绝、过期和“已保存令牌但缺少部分 scope”都以退出码 3 结束，因此无论结果如何，Bridge 都重新执行 `auth status --verify` 与目录读取，以复核结果为准；只有复核仍无可用身份时才发布 `mail_authorization_incomplete`。发起新的 `--no-wait` 不会作废已有令牌，所以“补充授权”失败时原有授权保持可用。

邮箱授权和可访问目录属于 Bot 的[连接复核](connector-architecture.md#连接复核)：每分钟及用户回到 Mochi 时复核，只在目录变化时才发布并记录 `connectors.rechecked`；从未授权的 Bot 不复核。选择邮箱使用最近一次的目录证明，不再为每次切换单独联网读取，所以开关在瞬间生效；飞书在每次读取邮件时仍按用户权限把关。设置窗口里短于 200ms 的操作不显示忙碌态，避免整窗变暗再恢复的闪动；宿主仍串行执行所有操作。Control 26 删除了不再有调用方的 `refresh_feishu_mail_connection`。

身份复核以 lark-cli 自己的服务端验证为准：`identities.user.verified` 与 `available` 都为 true，且 `status` 为 `ready` 或 `needs_refresh`。访问令牌约 2 小时过期；`auth status --verify` 遇到过期令牌会先刷新、再由服务端验证，但 `status`/`tokenStatus` 仍报告刷新前的 `needs_refresh`（lark-cli 1.0.93 `identitydiag.diagnoseUser`）。曾把这种情况误判为“需要重新授权”，2026-10-11 实机复现并修正。顶层 `verified` 属于当前生效的身份，不作为用户授权的依据。

授权在 Bridge 后台完成，与 GitHub 回调一致，不受“全部 Bot 空闲”闸门约束。首次授权（还没有已证明的授权）不改变正在进行的工作，Bot 忙时也可以发起；替换一份已证明的授权会在等待期间暂停邮箱读取，所以仍走空闲闸门，页面在 Bot 忙时禁用对应按钮并说明原因。选择变更走原有闸门；同一时间只签发一个 device code（两个窗口同时发起时第二个拿到同一个），连接器内部把复核与选择变更串行执行。

邮箱证明绑定在当前生效的飞书应用连接上（CLI、profile、配置目录、App、机器人身份与可用状态）。只有这份绑定变化时 Bot 才作废邮箱证明与飞书资料的复核结果；注册、检查、取消或丢弃替换候选不改变生效的绑定，也不会让已证明的邮箱授权失效。日志记录 `feishu.mail.authorization_started`、`feishu.mail.authorization_settled`（`outcome` 与复核后是否有可用身份 `proved`）和 `feishu.mail.authorization_start_failed`，不记录 URL、device code、用户 open_id 或邮箱地址。

跨边界失败使用邮箱专属的问题码：`feishu_mail_app_scope_required`（去飞书开通权限）、`feishu_mail_unavailable`（发起、取消、断开或打开开通页失败）和 `feishu_mail_selection_failed`（选择或取消选择失败，列表自动更新后重选）。它们不再借用飞书文档的提示文案。

## 实验验收：共享邮箱

实验只允许以下读取操作：

```text
mail.user_mailboxes.accessible_mailboxes   （确认用户可访问邮箱）
mail.user_mailbox.threads.list              （列出有限会话）
mail +thread --html=false                   （读取指定会话纯文本）
```

`threads.list` 使用 `folder_id=INBOX` 作为默认收件箱；飞书接口要求明确提供文件夹或标签，连接器不会依赖不存在的服务端默认值。

验收记录必须包含：用户身份已验证、目标共享邮箱出现在官方可访问目录、至少一个会话列表结果，以及一次指定会话的读取结果。正文只作为资料检查，不把其中的要求当作操作指令。

验收明确禁止调用 `+send`、`+reply`、`+reply-all`、`+forward`、`+draft-create`、`+draft-edit`、`+draft-send`、`message-modify`、`message-trash`、`threads.modify`、`rules.*` 或任何其他写入接口。实验不发送邮件，也不保存草稿，不改变已读、文件夹、标签或规则。

## 连接器边界

`feishu-mail` 的 provider、manifest、用户授权和邮箱选择由 `src/connectors/feishu-mail/` 独占；`feishu-service` 仍只负责机器人可读的文档/Wiki。两者可以使用同一 Bot 的官方 CLI transport，但执行身份和 scope 不混用：邮箱读取必须显式 `--as user`，不会用机器人身份冒充用户邮箱。

真实飞书组织审批、用户授权有效期、共享邮箱成员关系和邮件内容安全风险仍由飞书与邮件来源决定。Mochi 只在官方读取证明通过时调用，并在失效时失败关闭。
