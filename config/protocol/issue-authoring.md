# Issue 写作协议

把飞书讨论压缩成可追溯的 项目 Issue；不要把聊天流水账、方案猜测或权限规则写进正文。

需求或想法只保留：`要解决的问题或机会`、`希望发生的变化`、`已知约束与材料`。Bug 只保留：`实际问题`、`期望行为`、`复现线索与材料`。只有人类讨论已经确认时才增加验收标准、优先级或具体方案。

- 姓名、消息链接、时间和正文只以 `topic_evidence` 为来源；不要输出内部用户或消息 ID。
- “参与讨论”不等于负责执行；执行负责人只能来自明确认领或明确分配。
- 只保留 1–3 条真正改变问题定义、约束或结论的关键贡献，并链接原消息。讨论主导者属于 Agent 推断，必须标明推断；证据不足就省略。
- 图片与文件只写实际观察，并链接对应飞书原消息；不重新托管。无法读取、截断或降级时说明缺口怎样影响结论。
- Bridge 会在真正创建时自动追加权威来源话题、发起创建者和人类参与者；正文不要重复这些字段。

落实请求时，结合当前话题理解用户的完整意图；能从上下文确定事项和负责人，就不要让用户重复提供编号或复述要求。人类明确的“不新建”决定必须遵守，但不能把 Agent 自己说的“先记录”当成人类指令。若用户只说“分配给某人”而上下文没有可确定的已有 Issue，先询问目标或说明需要明确新建；不能为了完成分配而自行新建 Issue。

用户要求创建并分配时，把 `assignees` 放进同一个 `create` 动作，由模型结合当前上下文直接完成，不要额外制造确认轮次。已有 Issue 的明确分配要求直接执行。若 Bridge 返回可能重复的 Issue，模型应结合候选正文摘要和当前上下文选择复用或继续创建；必要时再读取候选详情，只有无法判断时才询问用户。回帖只据工具结果说明实际完成的操作，不能把期望负责人当成已分配事实。
