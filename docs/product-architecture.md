# Mochi product architecture

The current business boundary and Settings structure are defined by [Independent Bots](independent-bots.md). The target contract for an open external connector system is [Connector and Agent architecture](connector-architecture.md); it separates connectors, Feishu message channels, host model runtime and Skills. The older [plugin exploration](design/plugins-and-settings.md) remains a proposal for future capabilities, not the current navigation or account ownership contract.

The [Agent service contract](agent-service.md) defines how the host supplies usable capabilities, evidence, recovery information and delivery feedback. Runtime completion means a model turn ended; it is not a claim that the user's task succeeded. Feishu processing reactions clear after delivery, while audited waiting/blocked outcomes and execution failures remain visible. The service contract distinguishes missing primitive capabilities from the ability to compose existing tools for unanticipated tasks; the latter requires model behavior evidence, not task-specific feature additions.

## Product direction and implementation status

Mochi is a consumer product: each customer connects their own ChatGPT subscription or an explicitly configured Responses API compatible BYOK provider, a Feishu organization/Bot and selected resources, and the external connectors they choose. GitHub is the current recommended team-context connector; Feishu groups are the message channel, while the implemented Feishu Docs/Wiki adapter and future services are ordinary connectors. Bitable is a future capability until its own manifest and authorization contract exist. The accepted current scope, provider evidence and end-to-end acceptance live in [onboarding.md](onboarding.md); the target ownership and migration contract lives in [connector-architecture.md](connector-architecture.md).

Customer connections, shared onboarding/Settings, schema-6 customer-free installation and native registration delivery are implemented. The authorized September 8 development transition completed provider checks, offline schema/ABI migration, deployment and a real test-group reply. Remaining provider and installed-release acceptance are separate; the single evidence record is [the onboarding contract](onboarding.md#authorized-development-transition--2026-09-08). Do not use a new Session or erase live data to bypass outstanding gates.

## Current implementation

Mochi has one product boundary: a nontechnical macOS user opens one disk image, drags the real `Mochi.app` to Applications, and stays in that App for first-run setup, repair, and normal use. The disk image uses one reviewed static 1536 × 1024 Retina grass artwork in a 768 × 512 point Finder window: the approved composition and Mochi identity stay pixel-stable while a restrained cool slate grade, low-chroma olive grass and lifted lower plane make Finder's native black labels legible. The exact instruction `To install, drag Mochi to Applications` is baked into the upper field in warm-white SF Pro Rounded Regular, directly continuing the App's `.rounded` typography instead of introducing an editorial or generic installer voice. The 144 ppi asset preserves native 2× type edges and the source photograph's high-frequency detail rather than scaling a 1× raster. The mounted volume uses the exact `Mochi.icns` resource from the staged app as its hidden custom icon; that source icon keeps its rounded corners transparent, so Finder never renders an opaque white square around the volume icon. The image does not reuse the in-app character texture or pretend Finder can run time-aware or animated product logic. `Mochi.app` presents the one standard macOS administrator authorization needed for local isolation; its embedded package remains an internal privileged transaction carrier and never becomes a second product surface. Everything involving source checkouts, package managers, compilers, shell commands, service users, credentials, LaunchAgents, ACLs, sudoers, signing, and notarization belongs to release engineering or that internal transaction—not to product onboarding.

`script/build_product_package.ts` is the sole installation-visual authority: it copies the canonical artwork into `.background` and applies one Finder layout contract, including native black labels. Development builds write `Mochi-Development.dmg`; every release candidate contains the same native user-facing `Mochi.dmg`. There is no appearance argument, fallback asset, time-of-day branch, or second presentation contract. The running companion keeps its stable Mochi blue scene. Finder disk images do not run product code.

If the user opens the App from the disk image before dragging it, the same product surface stops before authorization, explains the one required Finder gesture, and reveals the source App. Setup failures stay inline with the setup step and one typed recovery action; they do not eject the user into a generic alert or expose lower-layer installer language.

## First principles

The **Settings → 嘱咐** document surface gives AGENTS.md a bounded, spacious writing area and one pinned save row, rather than nesting a small input above a second Done footer. Its Markdown text scrolls independently; failed saves and conflicting revisions retain the draft. Keyboard save uses the same validation and availability gate as the button. The independent Settings window retains its draft; the existing Bridge policy owner remains the only save path.

1. **One user action at a time.** First launch exposes exactly the next recoverable action: prepare the background, sign in, finish preparation, or wait.
2. **One authority for each kind of state.** Immutable product files live under `/Library/Application Support/Mochi`; mutable user state lives under `~/Library/Application Support/Mochi`; ChatGPT auth and Pi JSONL live only in the isolated runtime user; SQLite owns the active Session binding.
3. **No checkout at runtime.** Both deployments run a self-contained Bridge and native `lark-cli`, with the same separately isolated Pi worker. Their cwd is `/var/empty`; source, npm wrappers and terminal permissions are not runtime dependencies.
4. **Explicit irreversible transitions.** Model account connection does not create a Session. The user's explicit first “开始值班” action bootstraps, independently resumes and binds the first Session before enabling duty. New Bots default to paused; Settings, login and service startup never bootstrap.
5. **Fail closed across versions and authority.** One bundled compatibility manifest binds deployment mode and product/Bridge/status/control versions; worker protocol, capability ABI, LaunchAgent identity, worker digest, paths, and ownership are verified at their actual boundaries.
6. **Customer authorization, not secret-entry UI.** The ToC contract requires each customer's own grants, verified repository selection and a credential-free distributable. Installation prepares code and isolation; process-owned Feishu/GitHub connection modules obtain the customer's grants after launch. Neither a secret form nor a cosmetic connected checkmark is an enrollment authority.
7. **Recovery is part of the product.** Reopening Mochi repairs the same declared background state from its sealed embedded package. Two explicit uninstall modes make data retention explicit. Diagnostics export only typed health facts and coded events.

The event consumer runs the official CLI from inside that connection directory with `LARKSUITE_CLI_CONFIG_DIR=.`, so the socket the CLI creates is addressed relative to its working directory (`events/<appId>/bus.sock`) and macOS's 104-byte `sun_path` limit does not depend on where the customer's home directory happens to be. `HOME` and every stored file stay at their absolute paths; only the address the CLI binds is relative.

`src/product/layout.ts` derives user/Bot paths; the native helper consumes fixed installed roots generated from the product contract and keeps its matching narrow read-only continuity projection. The App takes the console user's paths (`userLayout`) from the same module, and a test binds the two sides in both modes. Both deployments have fixed roots and cannot be redirected to `/tmp`, a checkout, or another user's data by editing the plist. A Bot's identity is a local UUID, never a remote name, so a rename never moves a directory and a directory name never becomes a second identity. Development lives under `~/Library/Application Support/Mochi/Development/` with the same shape: `Runtime/bin` contains compiled Bridge/native Lark, `Runtime/Resources` contains protocol/build metadata/notices and `defaults/`, `Bots/<botId>` contains each Bot's mutable configuration and state, and `fleet.json` holds the roster. It shares the product's existing LaunchAgent/status/control endpoints, not a second background instance.

### Logs and diagnostics

`src/log.ts` is the one structured logger for the Bridge and the App. Each process picks its sink once: an owner-private JSONL file (directory 700, file 600, symlinks refused, 5 MB × 3 generations, each opened with the run marker), the console, or memory in tests (`bunfig.toml` preloads a memory sink, so test output carries no log lines). A record is `{ ...fields, timestamp, level, event }` with the reserved keys written last. A sink failure, such as a full disk or a refused symlink, never reaches the caller: the record is dropped, the first failure in a run prints one `log.write_failed` line to stderr (which the LaunchAgent discards), and the next record the sink accepts is preceded by `log.records_dropped` with the count. Bot-scoped records carry `botId`; the minute group recheck logs only a changed inventory. lark-cli reports connection state only as stderr text, so lines outside its known vocabulary are counted and warned as `lark.event.stderr_unrecognized` (1st, 2nd, 4th…). Worker stderr reaches the log only as the worker's own structured diagnostics, or as size and error class name.

The diagnostics export (schema 4) carries component versions, capability and problem codes, the selected Bot's health, a summary of every Bot (ID, lifecycle, phase, problem code, group and project counts) and the newest 50 allowlisted Bridge and App events, projected to stable codes and counts. It never includes names, chat or message IDs, error text, logs or paths. Native export failures keep their errno or panel code in the App log.

`script/deploy_development.ts` stages verified artifacts before stopping the service. `src/product/developmentDeployment.ts` owns its private, durable journal and same-volume code/plist publication/recovery; mutable state is never rolled back after a new process may have accepted an event. A bounded wait can leave a publishing journal after the new service becomes ready; `service:deploy --accept` verifies the current LaunchAgent and commits that journal, while `--rollback` restores the previous code when readiness cannot be proven. This developer-only transaction cannot provision the isolated Pi identity or alter the installed product. The separate existing `runtime:provision` maintenance entry compiles itself before requesting one native macOS administrator authorization, then checks the explicit Bridge user against the console account and hands that account the shared material parent exactly as the package does. It never asks for a terminal password or grants an interpreter persistent privilege; cancellation ends maintenance without running provisioning. This maintenance entry is not an App setup step and does not replace the installed package transaction. The privileged release package remains the sole installed lifecycle authority. First migration from a historical checkout requires explicit approval, stopped/locked source data, a retained private backup and exact database/binding proof; no runtime compatibility reader remains. App control manifest schema 3 rejects the retired interpreter/checkout LaunchAgent contract.

## Runtime composition

```text
index.ts → explicit offline maintenance, or Bridge host
bridge.ts → deployment lock, fleet.json, control socket, atomic status projection
  each BotApp → independent GitHubConnection + project selection
              → independent FeishuConnection + groups + event consumer
              → independent SQLite, instructions, policy and lifecycle
              → PiRuntimeClient → worker with this Bot's auth and permanent Session
```

The Bot owns memory, policy and external work authorization. The host owns process/transport facilities and the shared model connection; it has no GitHub grant. Desktop selection is only a view. Every Bot operation carries a Bot identity, while model account operations reject it. Shared account mutation acquires every Bot's idle admission gate before changing credentials; Bot pause and external connection changes remain local. See [independent-bots.md](independent-bots.md) for storage, lifecycle and explicit offline adoption.

`ProcessLock` holds each deployment, Bot and runtime-account lock through BSD `flock(2)` in a child of the already bundled Bun executable. It does not require the `lockf(1)` utility, which is absent on the supported macOS 14 target. The child opens the single-link, owner-private file without following symlinks, takes the lock and writes the owner PID through the same descriptor. Closing the parent's pipe or a parent crash releases it; an unexpected holder exit resolves `lost` and stops the owner. The lock inode and BSD locking semantics remain compatible with earlier deployments.

Package readiness requires the expected host/status/control versions and `controlAvailable: true`. Bot lifecycle belongs only to each `bots[]` entry; an empty fleet and unconnected customer accounts are normal after first preparation and do not prevent the installation transaction from completing.

`BotApp` owns the whole per-Bot lifecycle, including the first-run transition. A Bot with no permanent Session still runs and publishes `lifecycle: setup` with its stage; the customer's explicit `set_bot_enabled(true)` bootstraps the durable candidate, independently resumes it and atomically promotes it in that Bot's own SQLite before persisting enabled duty. Failure retains the candidate and prior duty state for explicit retry. Later duty starts only resume the existing binding. There is no separate setup process and no second control server. The retired Codex App Server remains absent. Missing GitHub registration fails that integration closed while preserving independent ChatGPT facts; successful login is not a verified project grant or completed product setup, and a deployment with no GitHub grant still starts every Bot with an empty catalog.

A Bot's start is its own failure domain: a Bot that cannot start publishes `lifecycle: failed` and leaves the others running. Host startup fails only at host boundaries such as the deployment lock, roster or control socket. Shared ChatGPT failure stops new admission across Bots without cancelling accepted work; Feishu/GitHub and Session failures remain local.

`BotRuntime` owns the serving state (`standby`, `unconnected`, `connecting`, `listening`, `failed`, `stopping`) and its allowed transitions. Admission and recovery consult this owner, never a published status snapshot. An event stream may change readiness only while it is the current stream and the Bot is serving; late callbacks cannot revive a paused or stopped Bot. Failed recovery preserves `failed` until a verified Session and new stream are established.

Accepted messages retain their original sender, text and FIFO position. `RuntimeSessionAgent` requests channel evidence and materials immediately before starting or steering that message, after any queue wait; a stale-turn steer refetches before its later turn. The Bridge rechecks the channel and model admission at that boundary. Unstarted messages hold no downloaded materials.

## Installation, update, repair, uninstall

`src/product/installation.ts` is the one schema-5 installation authority. It separates the disk-image-delivered host App from package-owned transactional components, and versions the installation-state migration, compatibility tuple, mutable retained roots, external identities, and both removal policies. `script/build_product_package.ts` is the only distribution entrypoint. It:

- validates explicit native GitHub registration, with no customer grant, Feishu secret or issuer RSA key; both packaging and privileged installation run the compiled Bridge's read-only `--validate-github-registration` command through the common maintenance dispatcher before publishing components;
- compiles Bridge and worker, verifies their version commands, signs both with the hardened runtime and exactly Bun's JIT entitlement (ad hoc in development packages) and proves JIT inside the exact signed bytes;
- builds the App with the same product version and an explicit package trust, `development` or the release's Developer ID Team; in-product setup checks the App against that Team (`codesign -R`) and lets root install only its private copy of the package after `pkgutil --check-signature` shows the same Team;
- copies the real `Mochi.app`, embeds the exact verified background package, signs the final bundle, and places only `Mochi.app` plus the canonical Applications Finder link in a branded `Mochi.dmg`; the single reviewed grass artwork carries its exact English instruction and keeps the lower plane deliberately lifted and quiet for native black Finder labels without sacrificing grass texture;
- bundles the pinned official native `lark-cli` (version and digest in `src/product/larkBinary.ts`) and all distributable license texts;
- writes the same generated manifest into Product resources and every native package, and puts all new immutable files under `/Library/Application Support/Mochi Installer/Payload` rather than their live destinations;
- uses Mochi's first-run standard macOS authorization prompt to run the internal package transaction that creates/verifies the service user, digest-pinned sudoers, the shared material parent, and LaunchAgent;
- embeds one cleanup entrypoint for the App’s explicit keep-data/delete-all decision, without publishing standalone uninstallers;
- in release mode requires exact same-Team Developer ID identities of the Team in `release/distribution.json`, one explicit notary profile, reviewed limitations, a clean source revision with its matching full verification receipt/log, and a private repository-external output directory;
- verifies the final signed App, embedded package, canonical Applications link, signed product components and final packages, waits for Accepted notarization results, staples and validates every ticket, requires Gatekeeper's Notarized Developer ID decision, mounts the disk image to prove its two-entry user inventory and exact embedded package bytes, then expands the final packages and byte-compares their staged payload, generated installation manifest and scripts;
- atomically publishes one manifest-digest-named candidate directory containing `Mochi.dmg`, the private internal product package and the exact `Mochi-Release.json` produced by `script/release_acceptance.ts`; schema 4 is the only candidate identity and binds source revision, supported architecture/macOS, limitations, sizes, and final SHA-256 digests without copying customer credentials.

The embedded package converges the background artifacts it owns through one bounded transaction. Before stopping a healthy service it verifies the installed host App and embedded package, validates every staged component and compatibility version, prepares digest-pinned sudoers, LaunchAgent and the installed contract record, creates any missing directory above a system component, proves every such ancestor lets other accounts search it and does not let them replace its entries, and proves every rename stays on one filesystem. Commit moves each previous component into a journaled backup before moving its staged replacement into place. The old set remains recoverable until the new Bridge publishes a matching setup/login/listening status; only then does finalize remove the payload and then the journal. The root-only journal under `/Library/Application Support/Mochi Installer/Transaction` is the only record of an unfinished transaction. Existing system ancestors are checked before directory creation: owners must be root or an administrator; non-sticky group write is limited to the administrator group, and extra ACL mutation grants are rejected. Read/search grants and stock deny-delete ACLs do not grant replacement authority. The three immutable macOS root aliases may normalize; other directory redirections fail closed. Existing administrator directories are preserved, never chmod/chowned to manufacture a passing audit. An error trap rolls back immediately; after a process or power interruption, reopening Mochi and repeating the in-app action replays the journal, restoring the predecessor, or finishing the cleanup of a finalized journal whose components still verify. Every lifecycle step checks its own result, because bash suspends `set -e` inside functions called under `||` or `if`: a failed step stops recovery with the journal and every unrestored backup in place, the package exits non-zero, and the trap does not restart a half-restored set. A journal records the account home its account-scoped paths resolve against and replays only for that account. Fresh preparation, same-version repair, and upgrade therefore use one path. Unknown installation-state versions, undeclared migrations, contract drift, and downgrades fail closed before commit.

The package runs with umask 077 and never relies on an inherited mode. It creates each missing directory above a system component, such as `/Library/Application Support/Mochi`, `/usr/local/libexec` or `/usr/local/share/doc`, one level at a time as root:wheel 755, marked with the `app.mochi.installer.created` extended attribute; a directory that already exists is never changed. Uninstall removes marked directories once they are empty, and no others. Directories in the console account's home are created and changed as that account; root there only renames the fixed-name LaunchAgent plist into place (and back on rollback) and, on delete-all, removes the declared data roots. Each of those root operations first enters the directory holding its target, proves from the directory actually entered (`/bin/pwd -P`; bash's own `pwd -P` re-resolves the remembered path) that no link redirected it, and then names the target relative to it, so the account cannot redirect root by swapping its directories for links mid-operation. `/Users/Shared/mochi` sits in a world-writable directory: root creates it in one step, or adopts it only while it is a real directory owned by root or the console account, refuses any other owner, and hands it over with `chown -h`. Bridge owns the material access policy. At every start `src/attachments/materialWorkspace.ts` sets that parent and its `materials/` root to mode 700 with exactly one ACL entry each for `_mochi` (traverse, then inherited read), replacing whatever was there, and does not start unless the result verifies exactly. The runtime sudoers rule exists once, in `src/runtime/sudoers.ts`; the installation manifest carries it with the Bridge account and worker digest as fields, which the package fills after checking the account against the same pattern. That pattern is the one account-name policy, which the update helper is compiled with too: macOS short names of letters, digits, `_`, `.` and `-` that start with a letter or `_`, except an all-uppercase name, which sudoers would read as an undefined alias that matches no account.

One installation serves the account its sudoers rule names. Update, repair and uninstall started from another account, including one reached by fast user switching, stop before changing anything. A fresh install binds to the account at the console when its postinstall starts; the remaining exposure is the seconds between authorization and that moment, and it can only set Mochi up for the account then in front of the Mac. The LaunchAgent names its deployment's App in `AssociatedBundleIdentifiers`; the exact name and publisher shown by Login Items must still be recorded on the release signature. The native host reads Apple's `SMAppService.statusForLegacyPlist(at:)` for that exact plist before projecting status or starting/restarting the service. A disabled item hides prior online facts and blocks control, with one action to open the system Login Items pane. Unknown authorization fails closed; the App never re-enables the item or infers permission from a successful `launchctl bootstrap`. Stopping remains available. Re-enabling is owned by macOS and does not change Bot data or Session identity. When macOS resubmits the legacy job through `smd`, only that launchd-reported ServiceManagement origin may replace the plist path; the installed plist, executable, arguments, working directory and Mochi environment must still match exactly.

Customer connection lifetime is separate from package lifetime. The package neither creates nor proves customer authorization; it validates only the native client registration and immutable components. Bridge Feishu candidate/proof/promotion and GitHub OAuth/selection own grants under Connections. Updating or repairing code never overwrites these user choices. Legacy recipient-package inputs, environment projections, enrollment receipts, profile staging and issuer RSA components are deleted rather than retained as a second mode.

GitHub write identity is remote and singular. The native Bridge holds the customer's rotating user token only to prove the human/App/repository intersection and to derive repository-scoped read capabilities. `mochi-github-authority` is the only issuer-key owner: it re-proves that intersection, mints a one-repository installation token internally, and executes only a versioned typed write endpoint. Neither the issuer RSA key nor installation token crosses back into the product. GitHub therefore records `mochi-companion[bot]` as the writer while SQLite preserves the requester, source message, authorization quote, and selection lineage. The model decides from the conversation whether a user question is needed; Bridge enforces typed scope, exact authorization provenance, idempotency and authoritative write readback. Current product capability remains Issue-only. Any future code or PR support must add a closed change-proposal transaction with its own authorization and workspace evidence; it may not expose a generic App token or reuse the user token for writes.

Data retention is manifest-driven. “关于与更新 → 卸载 Mochi” opens one native decision, defaulting to keep-data; deletion requires explicitly selecting all local data. The existing socket-activated root helper authenticates the signed App and console recipient, locks against updates, privately copies and verifies the current App/package and extracts that package's cleanup script. It shares Bridge idle admission with updates, including accepted turns, queues, schedules and final delivery, then requests App closure and stops the Bridge. Waiting can be cancelled. A root hold prevents a concurrent App launch from resuming intake while cleanup runs.

Keep-data removes the App, executable authority, LaunchAgent and sudoers while retaining policies, credentials, connections, permanent Pi history, logs and materials. The retained installation record is data, not a live deployment; reinstall prepares afresh over it. Delete-all also removes those product roots and the runtime account/group. Observed UI preferences, WebKit data and saved application state are declared in the same inventory. Inventory evolution allows only appending mutable roots: every existing entry, path and policy must still match exactly. This lets an earlier installation acquire the newly declared cleanup coverage without rewriting user data or weakening prior ownership checks.

The embedded cleanup runs with root credentials in the authenticated recipient's GUI audit session (`launchctl asuser`), so macOS can ask for system-administration consent when removing the hidden runtime account. A background daemon cannot display that consent even as root. The signed helper embeds the Mochi name and system-administration purpose; denial records `runtime-account-permission` and preserves all product files. The cleanup verifies account removal before deleting files, records the fixed selected policy and exact remaining paths, and removes the App last. A failure clears its intake hold and attempts to reopen the App with uninstall failure feedback at the top of About & Updates, visible without scrolling even in a short window; partial component removal may require in-App repair before retry. Repair selects the installed App even when a failed uninstall retains a private App copy; only an update request may select the staged update App. The update daemon is unloaded only after all cleanup succeeds. No separate installer UI, uninstall download or Terminal fallback is part of the product. Native cancellation, task draining, retention/reinstall and complete removal still require exact-candidate macOS acceptance.

## Arrangement ownership

[The arrangement contract](schedules.md) defines the Bot-owned calendar and delivery behavior. SQLite schema 9 holds definitions, at-most-once occurrence claims and delivery associations; a database at an older schema fails closed unmodified and is never upgraded in place. The existing Bot lock, permanent Pi Session and four-tool ABI remain authoritative. A new result discussion refers to the same arrangement without merging topics or borrowing historical human write authority.

`ScheduleDispatcher` accepts only idle, online work; authority preparation and delivery also hold admission against account/connection changes. `ScheduleStore` owns calendar state, revisions and run history, native Temporal owns time conversion, Pi owns transcript/model/compaction. Worker 11 independently enforces scheduled read-only execution. Control 24 provides on-demand scoped management, with no schedule body or run list in status 28 or diagnostics. No extra cron, service, cloud runtime or transcript database is introduced.

## Product setup protocol

Fleet status publishes host transport facts, the Bridge's `accountChangeReady`, one shared `runtimeAccount` and a `bots[]` list. The shared account may contain ChatGPT and up to sixteen named model API connections; each Bot entry owns its provider-qualified model policy in addition to its connector catalog, Feishu channel, character and lifecycle. Listening requires the shared account signed in and that Bot's original Session verified. Control requires a Bot UUID for Bot operations; renderer RPC additionally carries the Bot it displayed, so stale windows cannot act on a newly selected Bot. Shared login, cancellation, logout and account switching omit `botId` and are serialized with roster changes.

Control carries `botId` on the wire for every Bot-scoped command and omits it for deployment-level ones. There is no implicit current Bot: the desktop's selection is a view concern, and inferring it in the Bridge would let a stale window act on a Bot the customer is no longer looking at. `create_bot` returns the new `botId`; connector resource additions carry the Bot and verified connection reference.

Each Bot keeps one optional setup-stage projection plus one typed problem projection:

| Stage | Account proof | UI action | Allowed transition |
|---|---|---|---|
| `checking` | unknown; reading or unavailable | wait or typed recovery, never a guessed login | `signIn` or `ready` |
| `signIn` | signed out | Use ChatGPT login or configure BYOK | `signingIn` for OAuth, `ready` after BYOK validation |
| `signingIn` | OAuth pending | Reopen or cancel | `signIn` or `ready` |
| `ready` | official `openai-codex` OAuth subscription or `mochi-byok` Responses API | Finish preparation | `initializing` |
| `initializing` | signed in | none | active binding or `ready` with a typed problem |

`ui/setupPresentation.ts` owns copy, not state transitions. `host/presentation.ts` delivers encounter/intro/setup/companion with the same atomic frame channel; the renderer projects that surface rather than retaining a second `welcoming` flag. Native meeting preferences never certify provider readiness. The [entrance contract](entrance.md) records the reviewed native 24 fps full-body performance, real desktop transparency and measured scene-to-window handoff; generated acting and continuous spatial presentation share one timeline. The felt surface alone owns the shadow. The handoff opens the selected Bot's Feishu section in the independent `ui/SettingsApp.tsx` window, also reached from the home settings button, native menu and `⌘,`. Account/model/group modules own presentation and local drafts, not separate modals, credentials or provider state machines. No presentation event sends a test or asserts GitHub success.

`ProductProblem { version: 2, code, recoverability, recoveryAction }` is the only cross-boundary failure shape. Bridge status/control code owns the stable code-to-action mapping; companion validates that exact version and mapping before selecting its safe title and message. Setup, account, compatibility, service, connection, update/repair, and steady-state owners keep their structured internal cause but project no raw prose. Every product problem has exactly one next action. Unknown fields, versions, codes, or remapped actions invalidate the whole payload.

The status snapshot carries no Session/OAuth attempt ID, email, account avatar, token, message, raw error or filesystem path. Status 28/control 23 retain ProductProblem version 2. The shared model connection is a host fact; GitHub and project facts belong to their respective `bots[]` entries. GitHub facts expose only safe account login/ID, project facts and closed failure codes. Every Bot command names a Bot; GitHub login/cancel/disconnect/refresh accept only `botId`, while project selection additionally accepts bounded unique numeric repository IDs. Group participation still requires verified membership. All writes require authoritative companion read-back. Generic RPC, caller-selected Session/provider configuration and renderer credential input are rejected. Only the trusted native host may submit the closed `configure_byok` request. Diagnostics omit model API connection identity, GitHub identity/catalogs and group names/avatars.

`ByokAccount` owns a private array of up to sixteen `{provider,baseUrl,model,label}` declarations in `byok.json`; an old single object is read as the legacy `mochi-byok` record and rewritten on the next change. Pi alone writes API keys in `auth.json`. All ModelRuntime instances set `modelsPath: null`. The native model API form always shows `{baseUrl, model, label}` beside the secret field. Each named provider registers an exact image-capable model from Pi's bundled `openai-responses` catalog, including its context limit and supported thinking levels. Standard `/models` endpoints do not promise that metadata, so discovery never guesses missing capabilities or depends on a gateway-specific response. Arbitrary providers, headers, commands and unknown models are rejected. A bounded, no-retry request through Pi validates the endpoint/key/model using only in-memory credentials before committing them. Interrupted metadata without a credential remains signed out; a failed logout never clears metadata or claims success. A signed-in state proves that validation and credential commit completed, not continuous remote availability.

ChatGPT OAuth and multiple model API connections may be stored together. Each Bot's model policy stores the provider-qualified model reference, and its catalog includes every connected provider, so two Bots can intentionally use different connections while retaining independent Sessions and histories. Removing one provider does not log out the other; only Bots whose selected model belongs to the removed provider become unavailable and are directed to their own model settings. Credential mutations still acquire every Bot's idle admission because the Pi credential store and provider registry are shared. Model API changes alter neither the Bridge tool ABI nor Session lineage.

`lark/groups.ts` owns membership and participation, using official bot-identity `im +chat-list --page-all` at startup, every minute, on demand and before accepting an event from a group the inventory does not confirm, which while the inventory is unavailable is every group. It requires complete pagination, bounded to 1,000 groups; unavailable or incomplete inventory closes new intake instead of silently accepting a partial list. Reads coalesce and shutdown discards late results. `lark/group.ts` defines the strict projection `feishuGroups: { id, name, avatarUrl, enabled }[] | null`: null is unavailable, an empty array is confirmed empty. Names are bounded plain text and avatars are restricted to verified Feishu HTTPS CDN hosts. Missing or failed avatars use a local placeholder. This directory is not stream-health proof.

The user explicitly chose one shared permanent Pi Session per Bot across that Bot's joined groups, with new groups enabled by default. A second Bot has its own Session, so nothing it reads or remembers can appear in the first Bot's replies. SQLite stores only disabled `(app_id, chat_id)` choices; renaming, restarting and leaving/rejoining never erase those choices. Disabling stops new messages before buffering, hydration or runtime admission, while already accepted work finishes. Same-topic steering requires both chat and thread identity; other groups/topics queue into the same Session and reply to their own sources. Issue authorization remains chat/topic-scoped and is judged from the current conversation; Bridge no longer imposes a universal confirmation step. No new Session, fork or tool ABI is introduced.

The companion reads only fresh process-verified status, shows each Bot’s own participation count, and opens an accessible group list with persistent response switches. Names, avatar URLs and the group directory never enter diagnostics exports, logs or the model; structured policy logs contain only stable chat ID and the decision. Only public avatar image origins are added to renderer CSP; credentials and general network access remain unavailable.

The customer installation contract is schema 6 and contains no private enrollment or recipient environment. Legacy schema 3, 4 and 5 installations fail preflight before current components stop; no compatibility projection silently supplies customer authority. Moving the private deployment requires an explicit stopped-service reset of incompatible schema-5/6 Issue actions and a separately reviewed Pi capability-ABI migration. The reset preserves runtime binding, message idempotency, topic rows, group choices and Pi JSONL while deleting old Issue history; no old action is granted or replayed. Customer connections are established through their provider owners, not copied from old issuer inputs.

## Desktop ownership

Electrobun owns the native windows, application menu and WKWebView. Its main process is real embedded Bun; React receives only renderer-safe facts and the closed action union. The host reads the existing versioned status and sends the existing Unix-socket commands. `src/control/launchAgent.ts` owns the complete plist schema used by both service installation and companion verification; `src/control/protocol.ts` owns request/response parsing. The desktop never imports the service CLI or starts Bridge/worker executables.

`native/appkit.m` adapts the pinned Electrobun 2.0.1 root-view mirroring policy before any window is created. The SDK moves inactive webviews offscreen; on macOS 14, fitting a hidden Settings window to the display can leave its WKWebView at `(-20000, -20000)` after loading and renderer readiness, producing a blank window. Mochi's full-window webviews have no overlapping browser views and remain in place. Embedded views retain the SDK's original policy, including inspector handling. Missing or incompatible native methods fail host initialization; there is no resize timer or repaint retry. A framework upgrade must revalidate this boundary in native windows.

The desktop build preserves absent `MOCHI_PACKAGE_TRUST` as JavaScript `undefined`, meaning no package installation authority. Explicit development or Developer ID trust is validated at build time and startup; an empty or unknown value is an error. Build-only Apps must not encode absence as an invalid empty string.

The menu-bar extra has one `NSStatusItem` and `NSMenu` in `native/menu_bar.m`, reached only through `host/appKit.ts`. Electrobun 2.0.1's Tray serializer has no custom header or key-equivalent support, so it is not used alongside a second menu. The small felt identity header reuses the bundled App icon; the fixed 20 × 18 pt vector template adapts to system tint without animation. The [reviewed v3 pillow-shaped cat](assets/menu-bar-icons-v3.png) uses gaze, eye shape, ear posture, a small head tilt and a peeking crop for awake, replying, connecting, organizing, full, sleeping and attention. The nose, silhouette and optical bounds stay coherent; no external badges or continuous animation are used. Native code caches the seven images and only replaces the image when its state changes. `host/menuBar.ts` projects current controller facts, enabled-group counts, failures and service availability; it never consumes preview or activity history. Native code emits only show, settings, explicit start/stop and quit intents. The host rechecks availability and the explicit start/stop intent against the latest service state, then uses the existing controller; native code does not operate launchd. Quit retains Settings draft protection. `host/quit.ts` joins menu, Cmd-Q and native termination into one transaction: wait for the current controller operation, reject new operations, stop the verified LaunchAgent through `DesktopService`, and only then permit App termination. `host/processFamily.ts` observes the Bridge and its descendants using PID plus birth time, retains them across reparenting and waits for their exit after the job disappears. It never signals arbitrary PIDs; a failed or unprovable stop keeps the App visible and retains the tracked family for retry. Closing a normal window only hides it. The Bridge cancels GitHub work immediately and guards startup continuations; the Lark subscription joins its handlers and the official private-context `event stop` command before its lifetime ends, eliminating the detached bus idle tail without force-stopping another consumer. Reopening a stopped App offers Start and resumes the existing Session. Diagnostics remains in Settings and the application Help menu. The menu is initialized from the current snapshot before subscribing, and updates its existing items only when its projection changes.

One `DesktopController` owns product observations and operations for both windows. `host/presentation.ts` delivers the companion/intro/setup `DesktopFrame`; `host/settingsWindow.ts` owns one independent native Settings slot, and `settingsPresentation.ts` delivers current facts and one-shot closed routes after renderer subscription. Each slot rejects stale close/ready callbacks and requires its rendered surface before visibility: the companion supplies its drawn character frame; Settings acknowledges a React commit of real facts, nonzero layout and local-font readiness. Hidden WKWebView animation frames cannot serve as this gate. Settings never advances onboarding or resizes the companion. Reopening restores its route. `productRequests.ts` shares strict action/document validation and the existing controller between both trusted renderers.

`ui/SettingsApp.tsx` owns the three-column scope/category/content layout. Application scope contains shared model connection, diagnostics and help; Bot scope contains overview, instructions, model and thinking, groups and projects. Feishu and GitHub flows retain their independent owners. Navigation preserves per-Bot drafts and destinations, with reader return focus/scroll. Native close, Cmd-W and Cmd-Q use Electrobun's cancellable events, ask the live renderer for dirty/busy state with a five-second deadline and default to cancelling draft loss; unavailable state keeps the window. Settings has no persistent browser state or character canvas. Its neutral light theme, felt identity icons, its own control glyphs and bundled Bot portraits are used in both macOS appearances; native scope-rail material remains translucent.

`ui/BotHome.tsx` owns the selected companion's large state-animation stage and full-width window sill, reused by motion previews. The name and portrait-book trigger share the upper row; the lower row groups that Bot's duty switch, verified state and group avatars. The portrait book reveals each Bot's appearance, name and state, and selecting one only changes the view. The 124-pixel sill and character geometry stay fixed across lifecycle states.

`ui/store.ts` applies companion frames atomically. Connection failures and user-action failures have separate lifetimes: a healthy frame clears only the former. Settings has the same distinction in its window store. No competing initial snapshot read, delayed menu timer or replay queue exists.

`host/rendererReadiness.ts` joins subscriber readiness and the first painted character/error surface before revealing the native window. A 15-second first-frame deadline or explicit startup script/render failure produces a native failure instead of leaving an invisible App. Close cancels the deadline and revokes late callbacks. This is a bounded visibility handshake, not a provider retry or proof of desktop alpha. The current Three.js paper compositor has read-back checks for flat RGBA preservation, empty-pixel alpha, material coverage and reduced-motion geometry; it does not authorize new character poses or replace the video timeline.

At the start of a scene change, AppKit reports whether the source window is visible and unoccluded. `host/windowHandoff.ts` keeps the three paint receipts for a visible transition. A hidden, minimized or fully occluded source instead commits the target geometry and content directly, without showing or focusing the window: WebKit suspends animation frames for invisible pages, so waiting for them would incorrectly fail background recovery. This visibility fact stays in the native host; the renderer cannot use it to waive a visible transition's paint checks. `window.transition` records the chosen visibility alongside the destination surface.

`DesktopController` serializes user actions and drains coalesced observations without losing changes received during a read. It observes metadata of the exact status/plist/log files (including atomic replacement and initially absent files), schedules status expiration explicitly, and checks launchd at a 15-second observation ceiling. A verified launch identity may be reused only until that exact verified status expires, with unchanged configuration, PID and run identity; heartbeats never extend that lease. Every control command still forces fresh launchd identity verification. Background refresh cannot release an in-flight action gate. When a Mochi window gains focus, the host asks the selected Bot to recheck its connections; that request is neither exclusive nor busy, and the Bot publishes only what changed. Model writes require authoritative read-back; OAuth URLs stay in the host and open only in the system browser; initialization always requires an explicit user action. Closing the window does not stop the LaunchAgent. Only a failure to start or show the App itself ends it, with a native message; that exit leaves the LaunchAgent running, so Bots on duty keep working and the next launch reconnects.

Each release window restricts renderer navigation to its own bundled entry document (`index.html` or `settings.html`); both are emitted by the same Vite build. The user-approved development exception requires both a compile-time development build and a development manifest: only the exact loopback origin/entry supplied by this invocation of `app:dev` is allowed, without credentials, search or fragment. The launcher binds Vite to `127.0.0.1` on an ephemeral port, disables CORS and dotenv loading, and excludes private config, secrets and release artifacts from file serving. Vite and the App share one lifetime; a pipe held by the launcher makes its crash revoke the App too. Production rejects the development URL even if one is injected through the environment. CSP denies frames, forms and remote scripts/connections; remote images are limited to Feishu group-avatar CDN hosts and GitHub’s `avatars.githubusercontent.com`. GitHub project avatars use the verified catalog owner ID with the fixed `/u/<id>?s=80&v=4` image endpoint, so organization-owned repositories show their organization rather than the connected user; no arbitrary avatar URL or additional API credential enters the renderer. The development-only nonce permits the official React refresh preamble. No general Bridge, worker or renderer RPC capability is introduced.

`motion/manifest.json` remains the one source for characters, states, geometry, timing and preview menus. Unused Swift SF Symbol metadata is absent. The builder verifies original SHA-256 values and decodes approved WebP sequences into cached PNG atlases without changing any RGBA pixel. The renderer consumes the same manifest at compile time; the host consumes its byte-identical bundled copy. Original production WebP files stay in the repository; the shipped App contains only the decoded runtime projection, not duplicate videos. `motion/resources.ts` owns atlas layout and a 96 MiB retained-bitmap budget including stable poses; this is not a total browser/GPU-memory claim. Dimensions are validated before allocation, old unpinned atlases are closed before a new decode, and only one incoming decode may run. The displayed sequence remains pinned. Each character uses one fixed canvas/body baseline and must fit its stable poses plus two full sequences within that budget. State exits reverse the current video; loops finish at their shared root and continuous playback skips duplicate root holds. Static poses are not redrawn every animation frame. Reduced-motion and hidden-window behavior are explicit.

Hutch's documented `postBuild` hook captures the real inner Bun App before its generic self-extracting wrapper. `build/electrobun.ts` alone validates that SDK layout and adapts it to Mochi delivery; SDK drift fails before assembly. The adapter compiles the unmodified Electrobun bootstrap with the repository's pinned Bun, the runtime of the Bridge and worker, into the single `Contents/MacOS/Mochi` executable, then removes the SDK's own Bun and the bootstrap. `build/toolchain.ts` pins every downloaded build input (the Hutch archive digest and Hutch's recorded Electrobun core, Cottontail and Bun toolchain) and hands Electrobun's shim that exact Hutch, so a failed download never falls back to a machine-wide Hutch. The entry sets the SDK-required working directory before loading the bootstrap; compiled dotenv, bunfig, tsconfig and package.json autoload are disabled. LaunchServices and AppKit therefore retain the same executable identity for the process lifetime, without an `exec` handoff that invalidates macOS menu-bar registration. The adapter records that exact embedded runtime version for notices and owns no install/update policy. Electrobun's optional installer/uninstaller/update binaries are not shipped: `build_product_package.ts` and the existing installation manifest remain the only lifecycle authority. Leaves are signed before the bundle; both the main executable and final bundle signing pass retain the Bun JIT entitlement. The package builder reseals the entire nested graph after embedding its package. `build/attribution.ts` derives renderer notices from emitted JS modules and compiler CSS source maps, including shipped Tailwind styles; maps are inspected internally and never shipped. The host's SDK/schema imports and embedded Bun complete the notice inventory. Build-only libraries are not falsely listed as shipped code. Ad-hoc verification is not Developer ID/notarization or clean-Mac acceptance.

`bun run app:start` rebuilds and opens only the exact development bundle through LaunchServices, matching Finder. HMR alone launches the compiled host directly to retain its renderer capability and lifetime pipe. Bootstrap output goes to the private `~/Library/Logs/Mochi/desktop-bootstrap.log`, since LaunchServices cannot open redirected streams inside a protected checkout. The `--verify` alias rejects an early launcher exit and requires fresh `host.ready`, `menu.created`, `renderer.ready` and `motion-ready` events from the running `Contents/MacOS/Mochi` executable at that exact path. `menu.created` proves only local status-item creation: native acceptance must separately confirm the icon is visible and its menu actions work after LaunchServices launch; neither a successful build nor local menu creation proves system presentation. Logging and diagnostics follow [Logs and diagnostics](#logs-and-diagnostics). Deterministic coverage lives in Bun and WebKit tests, while native keyboard, accessibility, authorization and visual acceptance still require the real unlocked Mac.

First-run recovery stays inside the current setup step with one primary action. Preparation failures re-enter the same embedded package transaction; a failed browser open for the ChatGPT login reopens that pending login instead of initiating another one. Any other failed browser open, and an action on a Bot that has left the roster, is dismissed so the customer repeats it where it was; no recovery runs another provider's action. A service timeout is not completion and does not trigger automatic retries. `DesktopService` verifies deployment identity independently of status freshness: a prior PID's snapshot is unavailable evidence, never proof that the user opened the wrong edition. The host projects the current `eventStreamReady` fact to the renderer; historical activity is shown only as history and cannot claim the service is online. Product recipients never install or grant file access to a developer's Bun/Node/Pi interpreter. Development startup problems must not be passed off as recipient setup requirements.

Outside setup, the main panel displays the selected Bot’s full character above a compact nameplate, independent duty switch and group-avatar shortcut. The companion rail changes only the viewed Bot. Project access and the infrequent creation action belong in Settings. Host failures show one explanation and recovery action; stale Bot status is never displayed as online. `ui/accountPresentation.ts` owns the account-status labels: unavailable evidence remains unknown and never becomes an inferred logout. The first encounter and onboarding retain their existing character composition and handoff.

No retries, focus/reconnect refetch, optimistic policy writes or persisted cache. Model drafts and queries clear across account transitions. | Accessible controls and confirmations | Base UI switches/checkboxes; native AppKit confirmation | Provider controls retain their library keyboard and accessibility contracts. | Renderer build and HMR | Vite + official React plugin | One compiler configuration for production, development and WebKit fixtures. Pure helpers live outside component modules to preserve Fast Refresh boundaries. Native/host/manifest edits require a development restart; CSS/React edits do not rebuild the App. |
| Component styling | [Tailwind v4 + official Vite plugin](https://tailwindcss.com/docs/installation/using-vite) | One compiler for development, production and tests. Explicit UI-only source discovery; complete static utilities, data-state variants and one `@theme` for desktop typography/colors. The 4 px spacing unit preserves native point geometry independently of the 13 px body font. CVA owns button variants; clsx/tailwind-merge resolves composition. No component CSS selectors or copied theme stack. |
| Closed actions | Existing TypeBox | Derive the static type and strict host validator from one schema; no duplicated manual discriminator or permissive additional fields. |
| Formatting and lint | Biome | Desktop-owned source/build/config scope; hook correctness, accessibility and suspicious-code checks plus formatting/imports. Strict TypeScript remains enabled. Validated boundary/test non-null assertions are reviewed in context, not mechanically changed into silent optional behavior. No parallel ESLint/Prettier stack. |
| Local checks | Lefthook | Explicit one-time setup. Read-only checks of files selected by the staged diff; no auto-stage or destructive partial-commit formatting. Full verification runs once through `bun run verify` for the committed integration candidate. |

Tailwind replaces the previous component stylesheet, rather than sitting alongside it. `ui/style.css` contains only Tailwind imports/source declarations, theme tokens, global typography and OS preference rules. Per-component responsive and reduced-transparency behavior lives in utilities; only runtime asset URLs and manifest-derived geometry remain inline. `Controls.tsx` and `styles.ts` separate React components from pure variant helpers to preserve Fast Refresh. Browser tests select roles or explicit test IDs, never styling class names.

Motion is not installed. It is suitable for future interactive layout choreography, but it must not take ownership of the approved video timeline, fuzzy alpha composition or root-frame seams. The current UI has no such layout-animation requirement; adding a second animation clock now would not improve the product.


## 内置技能阅读路径

`config/protocol/*.md` 经原有发布入口进入部署 `Resources/protocol`。`src/agent/skillCatalog.ts` 声明固定协议身份与名称，`builtinSkills.ts` 同时供 `runtimeSystemPrompt` 与 `read_skills` 使用；后者不接收路径、ID、正文或任何写参数。Control protocol 24 返回完整、严格验证且序列化不超过 128 KiB 的 `{ id, name, content }[]`。失败返回 `skills_unavailable`，不以部分目录或 App 副本冒充运行内容。

App 经已验证后台的私有 socket 按需读取，只在当前阅读窗口缓存；断连清除并在恢复后重新读取。React Markdown + remark-gfm 负责正文语法，Tailwind 组件映射负责排版，正文没有 UI 字段 schema。内置协议互链只导航已发布 ID；外部引用以可复制地址展示，图片不加载，HTML 不执行。静态 PNG 图标属于 Vite 模块资源。


Development rollback restores the saved code and exact plist, then asks launchd to load that saved job. It does not parse the old release's status with the current decoder or claim product readiness; the matching App owns that verification. The Bridge LaunchAgent is `Interactive`: incoming user messages and companion controls require bounded response latency, and this socket-based service has no XPC activity contract for Adaptive scheduling. Background work limits are inappropriate for the digest-checked worker startup deadline. This changes scheduling, not process isolation or model/tool limits.

## In-app software updates

[The software-update contract](design/software-updates.md) owns user intent, idle handoff, local health and the signed feed. `DesktopUpdates` discovers and verifies immutable candidates, resumes only the same download and projects quiet status. The socket-activated native helper authenticates the caller with a kernel audit token, exact Developer ID requirement and executable path; it stages trusted bytes and invokes the existing package. The package is the sole owner of App/component commit and restoration. The stable lifecycle protocol shares the private Bridge socket but is independent of control version 28. Every accepted delivery must settle before admission closes. A new Bridge reads original Session history behind the root hold before external intake resumes. Journal finalization precedes hold removal; cleanup failures cannot undo committed work. Existing customer state remains outside component rollback. Native authorization, end-to-end upgrades and offline-window event delivery require the schema-8 installed acceptance evidence.
