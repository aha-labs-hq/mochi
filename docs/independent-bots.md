# Independent Bots

The September 20 Settings decision moves the ChatGPT connection into application settings. It supersedes only the per-Bot ChatGPT login in the September 18 contract. Mochi is the first Bot, not the owner of the other Bots. Every Bot still owns its instructions, permanent memory, model and reasoning policy, Bot-scoped external connections and selected resources, appearance, status and duty switch. The current product has GitHub project selection, Feishu group runtime access and the initial Feishu account authorization used by Feishu service capabilities; each service adapter still reports its own resource and capability state. A shared subscription never joins memories or external grants.

The September 28 connection update keeps the ChatGPT subscription and multiple named Responses API connections available at the same time. Each Bot chooses a model from a specific connected provider in its own policy; adding, editing or removing one connection does not silently rewrite another Bot's policy. The same all-Bot admission gates protect credential mutations, while a provider-specific model becoming unavailable blocks only the Bots that selected it until they choose another connection. The account worker owns private model API metadata and Pi credential operations, while the native host collects the key outside the renderer. The detailed provider and storage contract lives in [product-architecture.md](product-architecture.md).

## Ownership

The Bridge owns installation, the process lock, control transport, atomic fleet status and one `SharedRuntimeAccount`. The latter serializes provider changes with roster changes, while a dedicated account-only Pi worker performs ChatGPT login/cancellation/logout, model API add/edit/remove and account reads. That worker has no Bot identity, model policy, tools or Session. The host has no GitHub authorization, default Bot policy or selected Bot. Desktop selection is only a view. Bot operations name a Bot on the wire; provider mutations remain deployment-level because credential storage is shared, while model selection remains Bot-scoped.

A remote Feishu Bot can belong to only one local Bot; candidate verification and activation check the persisted bindings, including paused Bots, before accepting it. This prevents one incoming stream from feeding two independent memories.

A Bot owns one Pi client for conversation work, with an exclusive Session namespace derived from its validated local UUID: `.pi/mochi/bots/<botId>/sessions/`. All workers use the isolated runtime user's fixed `.pi/mochi/account/auth.json`; Pi's pinned credential store serializes token refresh and rereads changes across processes. Only the dedicated account worker accepts login/logout commands and holds `account/runtime.lock`. Bot workers retain their own namespace locks and cannot mutate login through the worker protocol. The Bridge cannot read credentials or transcripts. A separate verifier checks a newly bootstrapped Session after the first worker is released. Bot SQLite, instructions and external connection profiles remain under `Bots/<botId>/`. Shipped code, provider registration and character artwork remain immutable shared resources.

Pausing requires the target Bot to be idle; a busy Bot reports `connection_change_busy` without cancelling work. Pausing closes that Bot's admission, preserves its work record and connections, and releases its active worker. A shared account change reaches only the Bots whose model policy uses the connection it changes (every Bot when the target is unknown): it acquires each reached Bot's admission gate before pausing any worker, and active work, queued messages or compaction in a reached Bot reject it. A ChatGPT browser login changes no credential, so it pauses no Bot; status keeps the signed-in connections with `pendingLogin`, Bots on them keep working, and only Bots waiting for ChatGPT show `awaitingLogin`. After a change, reached Bots resume and verify their original Sessions; a failed Bot stays closed without preventing other verified Bots from working. Account-worker loss publishes `unknown` and stops new admission while accepted work finishes. A Bot's admission, never its displayed status, answers whether it is idle; the Bridge publishes the fleet's answer as `accountChangeReady`.

Messages that reach a Bot while a connection, account or organization change holds its admission are claimed and marked `OnIt` at once, wait behind the change, and are answered after it; if the change leaves the Bot unable to answer (paused, channel replaced, connection gone, stopping), the message fails with an honest reply in its topic. A worker or event-stream exit affects only its own Bot: that Bot reconnects itself after 5, 30 and 120 seconds, logging `bot.recovery.*`, and its attempts reset only after five healthy minutes. When they are spent it stays blocked with a `restartBot` problem, whose action reconnects that Bot alone; the service and other Bots keep running. Product shutdown remains a separate host operation.

Each Bot stores a `characterId` referencing the motion manifest. Appearance has no implicit relationship to capabilities, credentials or memory. The manifest remains the authority for artwork and motion. Future approved characters require no new Bot subclass or provider logic.

Each Bot also owns its arrangements in its existing SQLite database and state lock. The dispatcher uses only that Bot’s permanent Session and pinned resource selections; accepted schedule preparation and delivery count as busy for shared-account/connection changes. Arrangements do not steer with human turns or share authority across Bots. The schedule management query is Bot-scoped, on demand, and excluded from status and diagnostics. [The arrangement contract](schedules.md) owns delivery and time semantics.

## Upgrade and acceptance

Existing per-Bot ChatGPT logins require explicit offline adoption. The maintainer chooses one source Bot; the transaction archives every original account file and copies only that source into the shared account directory. Sessions, bindings, model policies and external connections do not move or change. Startup refuses unadopted credentials and incomplete receipts. Normal customers connect in the App; the maintenance command is not a setup step.

Acceptance covers two Bots using one login with distinct Sessions, policies and external connections; independent pause; fleet-wide idle admission for account mutation; initialization; original-memory resume; material isolation; offline adoption exclusion; and local failure isolation. UI verification includes scope navigation, first creation with an existing login, busy account controls, narrow layouts, keyboard access, draft retention and native rendering. Build and fixture tests do not replace real-provider evidence.

## Explicit offline upgrade procedure

Stop the old LaunchAgent and verify deployment/Bot locks are released. Build and provision worker protocol 11 through the existing runtime maintenance entry; provisioning does not adopt credentials or modify history. For fleet schema 2, run `runtime:account:adopt --bot <explicit source UUID>`. The maintenance entry holds the deployment and roster Bot state locks; the worker holds the shared account and all existing Bot runtime locks. Its resumable `account-adoption.json` receipt records source UUIDs and digests; `account-adoption-archive/<UUID>.json` preserves original bytes read-only. Credential content never crosses the worker boundary. Interrupted adoption resumes only the same source, verifies prior moves and refuses changed or ambiguous files. Repeating completed adoption cannot restore stale credentials after refresh/logout. Only then deploy/start the matching Bridge and companion and verify status 28/control 24. The shared account may then hold ChatGPT and multiple named model API connections; existing legacy `byok.json` metadata is read as one connection and migrated on its next edit.

The pre-0.2.0 development data migration (single Bot and fleet schema 1 to independent storage) is complete and removed.

The current registry and status contract is bounded to 64 Bots; this is a transport/resource bound, not a claim that 64 simultaneous model workers have been performance-qualified. Mochi, Awawa (a rock hyrax) and Kiwi have independent visual roots. Awawa's six local motion bindings, including the revised gaze performances, have passed the documented native preview and state-path review; Kiwi still uses explicit static state bindings. Current motion evidence belongs to `docs/motion-awawa-audit-2026-10-10.md`. Future capability differences need their own product contract, not a hidden meaning in the motion manifest.

Pi's pinned browser OAuth uses localhost:1455. A short-lived runtime-wide listener lock serializes browser login only; cancellation waits for provider cleanup, and attempts expire after five minutes. The existing Pi display patch also fails immediately on port bind failure and cancels its unused manual-code waiter. Provider URL/state/PKCE validation and token exchange remain owned by Pi.
